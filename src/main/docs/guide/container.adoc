Micronaut JAX-RS supports using JAX-RS annotations to define controllers.

Include the following server dependency:

dependency:micronaut-jaxrs-server[scope="implementation",groupId="io.micronaut.jaxrs"]

==== Resources

A class annotated with `@Path` is a root resource, and a sub-resource locator returns a sub-resource: an instance, or a class that is created like a root resource (JAX-RS 3.4.1). The JAX-RS rules apply: request matching (JAX-RS 3.7), parameter binding with `@PathParam`, `@QueryParam`, `@MatrixParam`, `@HeaderParam`, `@CookieParam`, `@FormParam` and `@BeanParam`, `@DefaultValue`, `@Encoded`, parameter converters, and the `@Context` types (JAX-RS 9). Resources are served next to Micronaut controllers, which keep the Micronaut behavior.

A resource class is created for every request (JAX-RS 3.1.1), with the values of the request in its constructor, fields and setters. A resource that is a `@Singleton` bean is created once; its `@Context` fields are proxies of the current request. Resources are beans: they can inject other beans, and the ones created for a request are destroyed with it.

The request entity of a resource method is read into memory before the reader interceptors and the readers run, up to `micronaut.server.max-request-size`. A request without an entity is not rejected with 415 for a `Content-Type` that the resource method does not consume, see <<supportedApi, Specification Support>>.

==== Bean Validation

With https://micronaut-projects.github.io/micronaut-validation/latest/guide/[Micronaut Validation] on the classpath and its annotation processor in the compilation, the resources are validated as JAX-RS specifies (chapter 7):

dependency:micronaut-validation-processor[scope="annotationProcessor",groupId="io.micronaut.validation"]

dependency:micronaut-validation[scope="implementation",groupId="io.micronaut.validation"]

For every request, in this order (JAX-RS 7.6):

. the fields and properties of the resource, and the constraints of its class, once it is created and injected; the constraints of a getter, also of a resource method that is a getter, are the ones of a property,
. the parameters of the resource method or sub-resource locator, including its entity and its bean parameters: a `@Valid` parameter cascades, and a `@BeanParam` without `@Valid` is validated too,
. the return value of the resource method: the value a `CompletionStage` completes with, for the constraints of the method and of its type argument, and the entity of a `Response` the method annotates with `@Valid`.

A violation of a return value is answered with 500, any other one with 400 and the messages of the violations. An `ExceptionMapper` of the application for the exception, e.g. an `ExceptionMapper<ValidationException>` or `ExceptionMapper<ConstraintViolationException>`, answers it instead. This applies to the resources that are beans and to the ones that are not, e.g. the sub-resources a locator creates; the validation advice of Micronaut Validation is not applied to the resource methods and locators, so they are validated once.

The executable validation rules of Bean Validation apply (JAX-RS 7.4): a resource method annotated with `@ValidateOnExecution(type = ExecutableType.NONE)`, or of a class so annotated, is not validated on execution. The groups are the default one, or the ones of the Micronaut Validation `@Validated` annotation on the method or the class, and `@ConvertGroup` converts the groups of a cascade. Setting `micronaut.validator.enabled` to `false` disables the validation of the resources too.

Not validated: the value an `AsyncResponse` is resumed with, the resources of `ResourceContext.getResource` and `initResource` until one of their methods is called, the constructor parameters of a resource, and a `null` returned for a `Response`. The fields and properties of a resource are validated from its introspection, which the JAX-RS processor generates for the classes annotated with `@Path`.

==== Asynchronous responses

A resource method with a `@Suspended` link:{jaxrsapi}jakarta/ws/rs/container/AsyncResponse.html[AsyncResponse] parameter answers when it resumes the response. On the Netty server, a link:{jaxrsapi}jakarta/ws/rs/container/CompletionCallback.html[CompletionCallback] is called once the response was written to the client: with `null`, also when an `ExceptionMapper` answered an exception, else with the unmapped exception, the failure of writing the response, or a `ConnectionClosedException` when the client went away. A link:{jaxrsapi}jakarta/ws/rs/container/ConnectionCallback.html[ConnectionCallback] is called when the client closes the HTTP/1.1 connection or resets the HTTP/2 stream before the response was written; the pending timeout of the response is then cancelled. On a server that does not report these, e.g. a servlet container, the completion callbacks are called once the response filters ran, and `register` does not register a `ConnectionCallback`.

==== Application

A link:{jaxrsapi}jakarta/ws/rs/core/Application.html[Application] subclass annotated with `@ApplicationPath` is a bean, and its path prefixes the resources. One `Application` is supported per application context, see <<supportedApi, Specification Support>>. The resources and providers it returns from `getClasses()` and `getSingletons()` are the only ones registered; an `Application` that returns none registers all of them.

An `Application` subclass without `@ApplicationPath`, which a servlet names with its `jakarta.ws.rs.Application` parameter, can be named with the `micronaut.jaxrs.application` property instead:

[source,yaml]
----
micronaut:
  jaxrs:
    application: example.MyApplication
----

==== Java SE Bootstrap

`SeBootstrap.start` starts a server for an `Application` at the protocol, host, port and root path of its configuration, with the application context of a Micronaut application. The instances the application returns from `getSingletons()` are its resources and providers:

[source,java]
----
SeBootstrap.Instance instance = SeBootstrap.start(new MyApplication(), SeBootstrap.Configuration.builder()
        .port(8080)
        .rootPath("/api")
        .build())
    .toCompletableFuture().get();
----

The resources and providers are created from the metadata the annotation processor generates, so the application is compiled with it like any other. `Instance.unwrap` gives the `ApplicationContext` and the `EmbeddedServer`.

`RuntimeDelegate.createEndpoint` is not supported and throws an `UnsupportedOperationException`, which the specification allows: start the Micronaut server, or use `SeBootstrap.start`.

==== Servlet Types

With `micronaut-jaxrs-servlet` on the classpath, a resource can inject a `HttpServletRequest` with `@Context`:

dependency:micronaut-jaxrs-servlet[scope="implementation",groupId="io.micronaut.jaxrs"]

In a servlet container it is the request of the container. On another server, such as Netty, it is a stub: a read-only view of the Micronaut request whose attributes are the properties of the request, without servlet context, session, request dispatcher or asynchronous processing, and whose entity is read by JAX-RS. There is no stub of `HttpServletResponse` or `ServletContext`.

==== Providers

Filters (`ContainerRequestFilter`, `ContainerResponseFilter`), interceptors (`ReaderInterceptor`, `WriterInterceptor`), entity providers (`MessageBodyReader`, `MessageBodyWriter`), `ExceptionMapper`, `ParamConverterProvider`, `ContextResolver`, `Feature` and `DynamicFeature` are registered as JAX-RS specifies (JAX-RS 4.1): a class annotated with `@Provider`, which is a bean, a class or an instance an `Application` returns, or a component a `Feature` registers. Each provider class has one instance per application. Filters and interceptors are ordered by their `@Priority` and bound to resource methods with name binding annotations or a `DynamicFeature`. The providers apply to the routes of JAX-RS resource methods only, not to Micronaut controllers.

The readers and writers of the application come before the standard ones, which read and write the types JAX-RS lists (JAX-RS 4.2.4), and before the Micronaut codecs.

The standard entity providers for `java.io.File`, `jakarta.activation.DataSource`, `javax.xml.transform.Source`, JAXB (classes annotated with `@XmlRootElement` or `@XmlType`, and `JAXBElement`), JSON-P and JSON-B are in a separate module:

dependency:micronaut-jaxrs-standard-providers[scope="implementation",groupId="io.micronaut.jaxrs"]

A `ContextResolver<JAXBContext>` of the application gives the `JAXBContext` of a JAXB type.

When the JSON-P API (`jakarta.json:jakarta.json-api`) and an implementation, such as Eclipse Parsson (`org.eclipse.parsson:parsson`), are on the classpath, the module reads and writes `JsonValue`, `JsonStructure`, `JsonObject`, `JsonArray`, `JsonString` and `JsonNumber` as JSON (JAX-RS 11.2.6), before JSON-B and the Micronaut JSON codecs. An empty or invalid entity, or a JSON value of another type than the parameter, is answered with 400.

When a JSON-B implementation, such as Yasson, is on the classpath, the module also reads and writes the JSON media types with JSON-B, and a `ContextResolver<Jsonb>` of the application or of the client gives the `Jsonb` of a type. JSON-B then reads and writes JSON in place of the Micronaut JSON codecs, except for the types of the other standard providers.

==== Multipart Entities

A `multipart/form-data` entity is read and written as a `List<EntityPart>`, and its parts are `@FormParam` parameters of type `EntityPart`, `InputStream` or `String`. The client sends one as a `GenericEntity<List<EntityPart>>`:

[source,java]
----
List<EntityPart> parts = List.of(EntityPart.withName("file")
    .content("file.txt", inputStream)
    .mediaType(MediaType.TEXT_PLAIN_TYPE)
    .build());
client.target(uri).request()
    .post(Entity.entity(new GenericEntity<>(parts) { }, MediaType.MULTIPART_FORM_DATA));
----

==== SecurityContext and Micronaut Security

When injecting the link:{jaxrsapi}jakarta/ws/rs/core/SecurityContext.html[SecurityContext] by default the injected instance is not aware of https://micronaut-projects.github.io/micronaut-security/latest/guide/[Micronaut Security] and methods like `isUserInRole` always return `false`.

To integrate the JAX-RS support with Micronaut Security add the following dependency:

dependency:micronaut-jaxrs-server-security[scope="implementation",groupId="io.micronaut.jaxrs"]

With the above dependency in place the `SecurityContext.isUserInRole` method will return `true` if the role is found within Micronaut Security's https://micronaut-projects.github.io/micronaut-security/latest/api/io/micronaut/security/authentication/Authentication.html#getRoles--[Authentication.getRoles()] method.
See https://micronaut-projects.github.io/micronaut-security/latest/guide/#retrievingAuthenticatedUser[Retrieving the authenticated user] for more information.
